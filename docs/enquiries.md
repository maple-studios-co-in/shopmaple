# Preview enquiry persistence

Contact, bulk and home/Nimbus project forms POST to `/api/enquiries` through the same-origin proxy. The API validates a bounded strict schema, requires the configured Origin, stores the enquiry in PostgreSQL, and returns only a reference with `mode: preview` and `notificationSent: false`. The UI states explicitly that the enquiry has not been sent to the team. No email or external notification is sent and no public read endpoint exists.

Each browser form generates an opaque UUID idempotency key. Retrying an unchanged submission, including after a lost response, reuses that key. Editing the payload creates a new key. The server stores a key hash and canonical payload hash; simultaneous identical requests return the same receipt, while a changed payload under the same key returns409 without changing the record. Form data remains in memory rather than localStorage. Keys are not durable across a full page reload, so this does not deduplicate independently submitted forms or multi-device enquiries.

Validation bounds names100, emails254, phones30, messages5000, product titles500, variant titles300, SKU160 and Indian pincode6digits. Bulk requests require name and phone. Strict schemas reject injected properties. JSON body limit16KB, private/no-store responses, and10submissions/hour per direct API client limit abuse. Production proxy/client-IP policy is not configured: the Next proxy can aggregate visitors under one loopback IP. Configure a known trusted proxy boundary and shared rate-limit storage before public rollout; do not blindly trust client-supplied forwarding headers.

Stored contact details are personal data. This development service has no staff inbox UI, authentication/authorization for retrieval, retention/deletion workflow or email worker. Those capabilities and production backup/access controls remain necessary before collecting real customer enquiries. Preview tests use synthetic example.invalid addresses.

Verification: five API tests cover persistence/receipt, concurrent retry/conflict, validation, origin/public-read rejection, body limits and rate limiting. Four client tests cover lost-response key reuse, edited-payload keys, malformed successful responses, bounded rate-limit errors and catalogue-length context. A mobile browser test submitted synthetic data and showed the saved preview reference. No email-delivery claim follows from these checks.
