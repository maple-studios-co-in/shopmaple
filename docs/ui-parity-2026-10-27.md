# Storefront UI parity and polish audit — 27 October 2026

Comparison of the live preview store (`https://store.maplefurnishers.com`, commit `c051b42` on `main`) against the incumbent Shopify storefront (`https://shop.maplefurnishers.com`) and the design intent in `DESIGN.md`, `docs/ui-parity-progress.md` and `docs/audits/2026-10-26-page-parity.md`. The audit ran in the Claude desktop built-in browser at a 1280×900 desktop viewport and a 375×812 mobile viewport. Screenshots are retained under `docs/audits/ui-parity-2026-10-27/` (`before-*` is the live store, `reference-*` is Shopify). No forms, carts, enquiries or payments were submitted.

## How the numbers were measured

Lighthouse is not installed on this machine and cannot be run from the built-in browser, so Core Web Vitals were collected in-page with buffered `PerformanceObserver` entries (`largest-contentful-paint`, `layout-shift`), `PerformanceNavigationTiming` and `PerformanceResourceTiming`. The session was not open in a window, so the browser pane ran as a background page: paint timings (FCP, LCP) are therefore inflated and are reported only where they are still informative; byte counts, request counts, cumulative layout shift and its sources, DOM size and image attributes are unaffected. Native lazy-loaded images do not load in a background page, so "thumbnail loaded" counts are reported as observed, not as a measurement of production behaviour. Repeat the paint measurements with the pane visible before quoting them externally.

**Where each number came from.** During this session the Mac's network intermittently refused `store.maplefurnishers.com` and `shop.maplefurnishers.com` (a Fortinet FortiGate filter presents its own TLS certificate and an insecure fetch returns a 403 block page, as confirmed by the coordinating session; `example.com` is not filtered). The block lifted for most of the audit window, so every "before" row and every Shopify "reference" screenshot in this document was captured against the live production store and the live Shopify storefront. Every "after" number was captured on `http://127.0.0.1:3000` running this branch's `apps/web` with `API_URL=https://store.maplefurnishers.com`, so the catalogue, media and API latency are production's while the Next.js server is a local dev build. ## Page-by-page findings

### Home

- **Layout and typography.** Header, announcement, hero split (workshop film + four green category tiles), "Decked for Diwali" banner, Maple Difference, categories, Nimbus, Instagram rail, testimonial, newsletter, values, cities and project form all match the source order and typography (Newsreader headings 40–72 px, Manrope body, Red Hat Display accents). The source shows a "Get 10% off" newsletter popup on first visit; the store does not (documented handoff).
- **Jank.** Cumulative layout shift 0.78 on desktop. Cause: every public route is `force-dynamic`, so the streamed shell paints `app/loading.tsx` (a 405 px tall logo state) with the footer directly underneath it in the first viewport; when the page streams in, the footer jumps ~5000 px. The same shift is 0.33 on `/collections/chairs` and will affect every route.
- **Images.** Four "Shop by category" covers are 1.8–5.7 MB SVG wrappers around embedded PNGs, rendered at 183 px, and the Nimbus background is a 2.3 MB SVG. `next/image` passes SVG through untouched, so the home page transfers 16 MB where the Shopify CDN also serves raster versions (`Cover_Image_Maple_N.webp?width=600`, 220–285 KB each, verified for covers 6, 7, 8 and 10). The workshop poster LCP image has `preload`; the 1920 px candidate is chosen for a 640 px slot at 2× DPR, which is expected.
- **Hover/focus/keyboard.** Category tiles scale on hover, carousels pause on focus, focus ring is visible. No issues found.

### Collection listing (`/collections/chairs`, `/collections/tables`, `/collections/beds`)

- The chairs route renders the bespoke editorial (newest arrivals hero, circular sub-collections, "A seat so beautiful" band, Best Sellers, room rails) above the filtered grid, matching the source structure. Tables and beds render the generic sidebar + grid.
- **Badges.** The source uses a solid red uppercase `SALE` badge at the top-left of a card; the store uses a pale yellow `Sale` badge. Visible on every bestseller card.
- **Keeri versus Shopify cards.** Keeri-sourced cards show "Price on request" (15 of 43 on page 1) and no compare-at price, Shopify cards show `Rs. 31,464.70` plus a struck compare-at. This is data policy, not a rendering defect.
- **Images.** The sub-collection circle for Sofas is the 1.78 MB `Cover_Image_Maple_6.svg` at 170 px. Product cards use responsive `sizes` and lazy loading correctly.
- **Jank.** CLS 0.33 from the loading-state footer jump. Mobile: the editorial circles and the grid were still unpainted several seconds after navigation in the background tab; verify with the pane visible.

### Product detail

- **Shopify-sourced (Aether – Crest, 40 images) and merged (Aero Dining Chair, 31 images).** Layout matches the source: vertical thumbnail rail, square stage, title, rating row, price block, option tiles, quantity + add to cart, customization panel, benefits, pincode, accordions, phone line, reviews band. Differences: the source shows "Taxes included. Shipping calculated at checkout." where the store shows the agreed enquiry wording; the source has three priced Aero options with photos, the store shows six (three catalogue options with "Photo unavailable / Price on request" plus three priced) — the known P1 identity issue in `docs/audits/2026-10-26-page-parity.md`, owned by the API.
- **Keeri-sourced (Imperio, 60 images).** Title, "Price on request", nine option tiles, enquiry button, accordions with real Keeri dimensions (`Width: 32" (≈ 81 cm)…`). Every option tile carries a grey "Photo unavailable" placeholder and the info column opens with "Photo for this option unavailable", although no Keeri product has per-option photos. Nine placeholder boxes dominate the first viewport on mobile.
- **Gallery with 40–60 images.** All thumbnails are rendered as full `next/image` elements with srcsets in one strip; the strip does not scroll to the selected thumbnail when the user uses the arrows, keyboard or swipe (at 40/60 the strip still shows thumbnails 1–7); adjacent images are not prefetched, so each arrow press waits for a network round trip before the crossfade; the focus outline of a thumbnail (4 px offset) is clipped by the strip's scroll box.
- **Cold image proxy.** First views of Shopify-hosted product images wait on `/_next/image` fetching and re-encoding from `cdn.shopify.com` (3–8 s observed). Keeri images (`/media/keeri`) are served from the same host and arrived in ~3 s.

### Story, policy and favourites

- `/pages/our-story` matches the source hero ("MADE DIFFERENT, BY DESIGN", italic tagline, four promise icons, belief panel).
- `/policies/privacy-policy` renders imported content with stray decorative glyphs ("◆", "◎") on their own lines before each highlight; the source hides these inside icon markup. Content import issue, not CSS.
- `/favourites` shows a clear empty state (heart, "Your wishlist is empty", Explore Collections). Saved items render as product cards.

### Header, footer, navigation

- Desktop header (utility links, centred logo, actions, five-item category bar) and the source-image footer match the source. Mobile header shows menu, logo, search and cart; the source also shows account and wishlist icons in the bar (recorded adaptation). Footer bands and the burgundy "Let's Build Something Lasting" contact band match.
- Keyboard: Tab order follows the visual order; the focus ring is the 2 px burgundy outline; dialogs trap focus and close on Escape; the gallery exposes arrow-key navigation when focused.

## Verification limits

The pane ran hidden, so FCP/LCP values were not reliable enough to tabulate and lazy thumbnails could not be observed loading; CLS, byte sizes, request counts and DOM attributes are reliable. The Shopify reference blocks non-browser requests (HTTP 429), so source comparisons are browser screenshots and page text only. No full-page pixel comparison, no every-breakpoint sweep and no production deployment are claimed by this document.
