# Checkout HTTP boundary

The API has a configuration-gated checkout HTTP boundary. `createApp(db, config, commerce)` accepts an injected order service; `server.ts` composes one through `commerce-composition.ts` only when `CHECKOUT_ENABLED=true` and the full commerce configuration is valid (see the checkout gate in [store deployment](store-deployment.md)). Otherwise the running preview returns `503 CHECKOUT_NOT_AVAILABLE`, health reports `checkoutEnabled: false`, and the cart still advertises checkout as disabled. When composed, `GET /api/checkout/options` publishes the configured delivery methods and the public Razorpay key id, and the `/checkout` page runs the hosted browser flow. Deploying this code does not activate live payments; configuration and the recorded release gates do.

## Routes when explicitly injected

| Route | Request authority | Result |
| --- | --- | --- |
| `POST /api/checkout` | Exact configured browser Origin, current `maple_cart` cookie, `Idempotency-Key`, strict `{}` JSON body | Freeze the current cart using stored prices and a server-side quote policy. Repeated keys for the same cart return the same attempt. |
| `POST /api/checkout/:attemptId/payment-order` | Exact configured Origin, current guest cookie, UUID attempt ID, strict `{}` JSON body | Create or replay the provider order for an owned attempt. The durable attempt ID supplies idempotency; no client amount, currency, merchant, reservation or payment fields are accepted. |
| `GET /api/checkout/:attemptId` | Current guest cookie and UUID attempt ID | Return only an owned attempt's public status. Unknown, expired and other-cart credentials cannot read the attempt. |
| `POST /api/checkout/:attemptId/release` | Exact configured Origin, current guest cookie, UUID attempt ID, strict `{}` JSON body | The buyer walked away from a payable attempt (edited details, re-quoted). Frees the Keeri hold best-effort and marks the attempt `abandoned`; an uncertain release leaves `reconciliation_required` with `RELEASE_UNCERTAIN` and answers 409. Idempotent. |
| `POST /api/checkout/:attemptId/payment-callback` | Exact configured Origin, current guest cookie, UUID attempt ID, strict `{ razorpay_order_id, razorpay_payment_id, razorpay_signature }` | Razorpay's browser success callback. The signature is checked with the key secret (401 when wrong) and the payment is queued for the same leased, fetch-verified check as a webhook; answers 202 with the public attempt. A callback alone never marks anything paid. |
| `GET /api/checkout/options` | None | Configured delivery methods and the public Razorpay key id; 503 when options are not configured. |

A quote whose unit price differs from the price the store shows answers `409 PRICE_CHANGED`. A quote whose delivery line was not priced by Shiprocket (Keeri fell back to its policy amount, or stated nothing) answers `422 DELIVERY_UNPRICED` and freezes nothing; the page offers an enquiry instead. The one exception is free delivery that Keeri states outright (see "Free delivery" below). A payment Razorpay confirms after Keeri's hold lapsed becomes `paid_hold_lapsed` (reported `paid: true`, `fulfillmentStatus: review_required`) and goes to staff (`docs/checkout-recovery.md`).

The checkout body may carry an optional `promoCode` (3-24 capital letters and digits once trimmed and uppercased), which goes to Keeri's quote unchanged. It is part of the checkout input, so a different code (or none) is a different quote for the idempotency key, replay and `CHECKOUT_INPUT_CHANGED`. A promoted quote carries `promotion: { code, label, discountPaise }` and, on every item, `discountPaise` and `undiscountedUnitPricePaise`; the store checks that each line's discount is what its unit price lost times its quantity, that they sum to the promotion, and that the price before the discount is the price the store shows. Its totals are already discounted and `totalPaise` is what Razorpay charges. Keeri's 422 promo refusals answer `422` with their own code and message: `PROMO_NOT_FOUND`, `PROMO_NOT_RUNNING`, `PROMO_NOT_APPLICABLE`, `PROMO_ALREADY_USED`. When the hold is refused for the code (`PROMO_NOT_RUNNING`, `PROMO_ALREADY_USED`) nothing is held: the attempt becomes `abandoned` with that `failureCode`, and the buyer may quote again with another code or none. An item the store can no longer link to Keeri, or that Keeri no longer sells online (`CATALOGUE_BINDING_REQUIRED`, `RESERVATION_NOT_ELIGIBLE`), answers `422 ITEM_NOT_BUYABLE`.

A cart with an attempt in `reserving`, `creating_provider_order`, or `awaiting_payment` with a live reservation cannot be quoted again (`409 CHECKOUT_IN_PROGRESS`) until that attempt is released, abandoned, captured or its hold expires. A delivery method outside the configured options, or a Keeri 4xx refusal, answers `422 QUOTE_REJECTED`; a Keeri 5xx or transport failure answers `503 QUOTE_UNAVAILABLE`.
| `POST /api/webhooks/razorpay` | Exact raw-body HMAC, `x-razorpay-signature`, `x-razorpay-event-id` | Persist authenticated receipt and return `202 {"accepted":true}`. Payment verification and order delivery happen separately. |

The response DTO is an allowlist: `id`, `state`, `amountPaise`, `currency`, `paid`, `providerOrderId`, `payBy` (two minutes before the hold lapses; the payment window closes then), and for v2 quotes the items with their fulfilment, totals, and the chosen courier's name and transit estimate. It excludes frozen item snapshots, SKUs, cart IDs/tokens, merchant scope, reservation IDs, receipts, payment IDs, internal failure codes and provider responses. Each quoted item also carries `localVariantId`, the store's own id for the piece from the catalogue bindings frozen with the quote: the id the cart uses, which differs from Keeri's `variantId` for a variant carried over from the old store, so the storefront can show the photo it kept for that piece. Nothing else from the bindings is returned, and an attempt frozen without them has none. `paid` becomes true only for the service's verified `captured` state. An accepted webhook is not payment confirmation.

Checkout and webhook responses use `Cache-Control: private, no-store`. The normal API rate limiter also applies to the webhook. The application continues enforcing Origin on browser mutation routes, including checkout. Only the exact machine POST path bypasses browser Origin checks; suffixed and trailing-slash paths do not. The webhook parser runs before the generic JSON parser, accepts only uncompressed `application/json`, and caps the raw body at 64 KiB. Authentication happens in the existing gateway before any inbox database write. The HTTP layer deliberately does not synchronously process the event or contact the provider.

Guest credentials must contain exactly one well-formed `maple_cart` cookie. Existing service checks enforce cart expiry, cart ownership and merchant scope. Missing or mismatched credentials receive the same public not-found response. Body and key validation failures return 400; invalid HMAC returns 401; oversized webhook bodies return 413; unsupported encoding/content types return 415. Domain failures are translated to safe public messages without internal error details.

## Free delivery

Staff can flag a variant "free delivery" in Keeri (Channels → ShopMaple). The store never decides this itself; it only recognises what Keeri's quote says, in the snapshot's `delivery` record (`packages/contracts/src/checkout.ts`, shared fixture `docs/contracts/shopmaple-quote-v2-free-delivery.json`):

- **Every item flagged:** `source: "free"`, `carrierPriced: true`, `fallbackReason: null`, `carrier` naming the Shiprocket courier that confirmed the pincode, `freeDeliveryVariantIds` listing every item, and `shippingPaise: 0`. This is the only delivery line that can be paid without a carrier's charge. Keeri still asks Shiprocket about the whole parcel first, so a pincode the courier cannot reach arrives as a policy fallback and is refused as before.
- **Some items flagged (mixed cart):** `source: "carrier"` as usual, plus `freeDeliveryVariantIds` naming the flagged items. `shippingPaise` is Shiprocket's rate for the other pieces alone.
- **Nothing flagged:** the record is exactly what it always was.

`freezeCart` checks the record rather than trusting it: the named items must be this quote's own, each once; `free` must cover every item and charge nothing; a carrier price may leave out some items but never all; a policy fallback names none. A contradiction is `QUOTE_INVALID`. Then the payment rule accepts `carrier` or `free` only when a courier is named, `carrierPriced` is true and there is no fallback reason; everything else, including a zero policy amount, is still `DELIVERY_UNPRICED`.

The public quote adds `delivery.freeDelivery: { all, titles }` only when free delivery changed the charge; an ordinary charge's `delivery` is unchanged. The checkout shows "Free delivery" on the delivery option when `all` is true, and for a mixed cart keeps the charge and adds "Free delivery on <pieces>. The delivery charge is for the rest of your order." Order summaries, emails and the order pages already print "Free" for a zero delivery charge; the staff order alert says the delivery was free and which courier ships it.

**Release order.** The quote schema is strict, so a store release without this change rejects any quote that carries `source: "free"` or `freeDeliveryVariantIds` (the buyer sees a failed quote; nothing is charged). This release must therefore be live before Keeri staff tick the first variant. Keeri emits the new fields only for flagged variants, so the two deploys can go in either order. If the store is ever rolled back past this release, untick the flagged variants in Keeri first; orders already placed with free delivery keep their payment and Keeri order, but an older store cannot show their quote lines.
