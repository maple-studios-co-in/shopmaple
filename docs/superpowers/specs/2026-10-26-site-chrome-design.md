# Navigation and footer content controls

This implements the existing user-authorized Shop Admin goal: content/copy/position controls with original Shopify defaults; Keeri owns catalogue/commerce. Use the current typed draft/publish/revision system, not a new service or raw HTML editor. No production publication, account provisioning or checkout activation occurs here.

## Shared contract (implementation interface)

Optional `StorefrontContent.siteChrome: SiteChrome`. Omission preserves legacy/default rendering. Export `siteChromeSchema`, `SiteChrome`, `ChromeLink`, `ChromeNavigationItem`, `ChromeNavigationColumn`, `ChromeNavigationLink`, `ChromeActionLink` from contracts.

- `ChromeLink`: `{id:string,label:string,href:string,enabled:boolean,enquirySubject?:string}`. Stable id canonical lower-case alphanumeric/hyphen <=80; nonblank label <=120; href existing canonical contentLinkSchema or exactly `/account` or `/favourites`. Optional nonblank enquirySubject <=160 only when href is exactly `/pages/contact`; renderer builds `?product=` using URLSearchParams. No raw arbitrary query strings, external destinations, fragments-only links, credentials, admin/API paths or script markup.
- `ChromeNavigationLink`: ChromeLink plus `parent:boolean` (source parent typography).
- `ChromeNavigationColumn`: `{id:string,links:ChromeNavigationLink[]}`;1..12 links, unique IDs per column.
- `ChromeNavigationItem`: `{id:string,label:string,href:string,enabled:boolean,feature:'living'|'bedroom'|'none',columns:ChromeNavigationColumn[]}`;0..4 columns, IDs unique per item. href canonical store destination (no enquirySubject at group level); for a submenu it is the feature-card View all destination, otherwise its direct destination. Feature preset retains existing original artwork and never controls inventory. Living preset shows the existing Living Room featured product selection; root shows existing main featured selection. All featured prices/publication remain current catalogue authority from PR41.
- `ChromeActionLink`: ChromeLink plus `cta:string` nonblank <=80.
- `SiteChrome`: `{announcement:{text:string,href:string,enabled:boolean},utilityLinks:ChromeLink[],navigation:ChromeNavigationItem[],desktopDiscovery:ChromeActionLink[],mobileQuickLinks:ChromeLink[],footer:FooterContent,whatsapp:{enabled:boolean,phone:string,label:string}}`.
- Announcement text <=200 nonblank, href canonical store link. utilityLinks0..6; navigation1..8; desktopDiscovery0..6; mobileQuickLinks0..8. All lists unique IDs.
- `FooterContent`: `{columns:Array<{key:'shop'|'help'|'care',enabled:boolean}>,contactColumns:Array<{key:'bulk'|'service'|'marketplace',enabled:boolean}>,shopHeading:string,helpHeading:string,careHeading:string,shopLinks:ChromeLink[],helpLinks:ChromeLink[],policyLinks:ChromeLink[],addressLines:string[],customerPhone:string,customerPhoneLabel:string,customerEmail:string,contactHeading:string,bulkHeading:string,serviceHeading:string,findUsHeading:string,bulkPhone:string,bulkPhoneLabel:string,bulkEmail:string,copyrightName:string,instagram:string|null,linkedin:string|null}`.
- Footer layout lists contain each of their three fixed keys exactly once, order editable. shop/help lists0..12, policies0..8, IDs unique per list. addressLines1..4 each nonblank <=160. Headings/copyright <=160 nonblank, phone labels<=60 nonblank. Phone raw canonical E164 `+` then8..15digits; mailboxes valid email<=254 with no header injection. Social HTTPS canonical Instagram profile / LinkedIn company URLs only, no credentials/ports/query/hash/encoded tricks. null hides icon. WhatsApp uses validated phone; label nonblank<=120; renderer strips initial+ for wa.me URL.
- Strict objects and control-character rejection throughout. Bound global content128KiB as existing. SiteChrome itself max64KiB. Cross-field errors return normal content validation responses.

## Defaults and public rendering

Renderer owns `apps/web/lib/site-chrome-defaults.ts` exporting `defaultSiteChrome`, `resolveSiteChrome(value?:SiteChrome):SiteChrome` with deep clone fallback, and `chromeHref(link:ChromeLink):string`. Preserve literal current header/footer labels, contact overrides, source navigation ordering/parent flags and safe existing default enquiry subjects from # source links. Existing source nav becomes stable positional IDs before labels are editable. Submenus and keyboard focus use IDs/presets rather than edited labels. Do not let renaming Living Room/Bedroom change artwork, selected state, drilldown or Back focus.

Layout reads published-only content through existing server reader and passes only the siteChrome slice to StoreChrome/Header/Footer/WhatsApp, not the full document or drafts. Old snapshots/no publication/read failure retain original defaults. Avoid importing admin/editor/whole content data into the public client bundle. Keep admin route isolation and default component props for existing callers/tests. Header actions/search/cart semantics remain. Footer reorders/hides its defined columns with current CSS structure. All-hidden lists should not emit empty navigation regions/headings.

## Editor

A Navigation & footer tab edits this optional slice, starting from a deep clone of source defaults. Support add/remove/reorder/toggle on link lists, navigation items, columns and column links within bounds; edit labels/local href, optional enquiry subject, parent style and feature preset. Stable IDs generated once; IDs are not derived from mutable labels. Support source reset by removing siteChrome override (existing default). Footer column/contact column order+visibility, headings/address/contact/social details, announcement and WhatsApp controls. Label inputs, show bounded constraints, retain invalid in-progress text until Save reports schema errors, and keep keyboard focus on moved/removed controls. Existing dirty/save/conflict/publish/rollback semantics govern all changes. No publication side effects from typing/reset/reorder.

## Backend publication validation

Extend current candidate-document internal-target checking for enabled chrome destinations, including navigation descendants only under enabled items, enabled discovery/utility/quick links, enabled footer sections and bottom policies, announcement when enabled. Recognize existing account/favourites routes. Existing custom pages and newly authored articles in same candidate are valid. Product targets require current published product in same transaction. Missing enabled targets reject publication atomically and keep previous public revision. Disabled destinations may remain in drafts/document for later editing, but re-enabling must pass publication. No schema migration or new auth permission is required. Existing auth/role/CSRF/revision protections remain.
